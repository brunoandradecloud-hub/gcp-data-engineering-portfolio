## 📚 O que eu estudei hoje

### 🧊 Bigtable: o que é e quando usar (NoSQL operacional)
* **Wide-column, baixa latência (ms), alto throughput**: feito para serving rápido e ingestão pesada.
* **Separação de responsabilidades na arquitetura**:
  * Bigtable = **serving operacional** (consulta por key, baixa latência).
  * BigQuery/BigLake = **analytics/histórico longo**.
* Cenários típicos: **IoT/telemetria**, estado por entidade, flags/alertas, time-series operacional.

### 🔑 Row Key: o segredo da performance
* Row Key define **ordenação** e como Bigtable forma **tablets** (ranges de chaves) — isso define distribuição de carga.
* Boas práticas:
  * **Evitar timestamp puro no início** (gera hotspot de ingestão).
  * **Reversed timestamp** para ler os mais recentes primeiro em time-series por entidade.
  * **Sharding/Salting** (prefixo hash) para espalhar escrita quando poucos IDs concentram tráfego.
* Técnica adicional “PDE-friendly”:
  * **Reverse Domain (Reversal):** `com.google.search` em vez de `google.com/search` para reduzir concentração por prefixo dominante e permitir prefix scans mais eficientes.

### 🧩 Tablets, split e hotspotting
* Bigtable escala por **tablets**; hotspot significa “poucos tablets recebem quase todo tráfego”.
* Insight importante: aumentar nodes pode aliviar, mas **não corrige hotspot** se a Row Key continuar concentrando acesso.

### 🧹 Garbage Collection (GC) no Bigtable
* GC é política por **Column Family**:
  * **TTL** (age-based) e/ou **Max Versions** (version-based).
* GC não é “perder histórico”; é o contrato de retenção para manter Bigtable **magra e rápida**.
* Padrão recomendado: **histórico longo** vai para BigQuery/BigLake; Bigtable mantém janela operacional ou estado atual.

### 🧭 Diagnóstico: Cloud Monitoring vs Key Visualizer
* Estratégia correta:
  * **Cloud Monitoring** primeiro (visão macro): latência, QPS, erros, throttling, saturação.
  * **Key Visualizer** depois (visão micro): identificar hotspots por ranges de Row Key.
* Regra prática:
  * CPU global baixa + latência alta em subset → provável **hotspot/key design/padrão de acesso**.
  * CPU alta + throttling global → provável **capacity** (nodes) + tráfego legítimo.

### ♾️ Padrão moderno: Pub/Sub → BigQuery → Continuous Query → Bigtable
* Faz sentido como **ELT near real-time** + **reverse ETL**:
  * BigQuery (landing + decisão via SQL contínuo)
  * Bigtable (serving em ms por key)
* Importante: não substitui Dataflow quando você precisa de **event-time/windowing/state/late data** avançado.
* Bigtable **não possui** um “direct subscription path” igual ao BigQuery; normalmente entra Dataflow/Run como writer quando o caminho é Pub/Sub → Bigtable.

### 🏢 Troubleshooting (labs): BigQuery Editions / Reservations
* Erro encontrado: exportar para Bigtable exigindo **reservation** (BigQuery Editions).
* Regra crítica: uma reservation **não pode misturar** assignments **CONTINUOUS** e **não-CONTINUOUS** (ex.: QUERY) → precisa separar em reservations diferentes quando o lab exige ambos.
* Entendimento do motivo: isolamento de capacidade e tipos de job.

## ⚠️ Pontos de Atenção (Armadilhas de Prova)

* **Timestamp no início da Row Key** → hotspot quase garantido em ingestão.
* **Sharding** resolve escrita, mas complica leitura por entidade (precisa ler múltiplos shards).
* **Multi-cluster routing** pode ser **eventual**: pode falhar o “read-your-writes” se você ler em cluster diferente do write.
* **GC por column family**: aplicar TTL/versions errado pode remover dado importante ou inflar rows/versions e piorar latência.
* **Reservations**: não misturar `CONTINUOUS` e `QUERY` na mesma reservation (FAILED_PRECONDITION).
